## 1. Что просят (сводка из задачи)

- Новое React-приложение, **одна страница**, **без роутинга, без памяти, без стейт-менеджера** — только локальный стейт.
- Слева `textarea` с **Mermaid-разметкой**, справа — **превью схемы** (DOM или canvas — не важно).
- Рядом с превью — **кнопка «Скачать изображение»**.
- **Пользователь не может менять стили.** Оформление — только «стиль Нетологии».
- Дизайн схем — «как в архиве» (референсы), но там слайды противоречат друг другу; **нам разрешено стандартизировать и задать правила**.
- Если в прямоугольнике много текста — **не растягивать прямоугольник, а уменьшать шрифт** (fit-text и аналоги).
- Разрешено (и рекомендуется) сделать **свой DSL**: Mermaid → обогащённый JSON → по нему рендер.
- Ориентир по продукту — аналог `https://mermaid.ai/`.

### Чего в задаче нет (и я не добавляю без согласования)

Сохранение в localStorage/бэкенд, история, шаринг ссылкой, редактирование схемы мышью, тёмная тема, мультиязычность, авторизация.

## 2. Что уже проверено фактически

### 2.1 Mermaid умеет отдавать разобранную модель без рендера `[ПРОВЕРЕНО]`

Поставил `mermaid@12.2.0` локально и прогнал реальные примеры. Работает:

```js
const res = await mermaid.mermaidAPI.getDiagramFromText(text)
// res = { type, text, db, parser, renderer }
const db = res.db

db.getDirection()   // 'TD' | 'LR' | ...
db.getVertices()    // Map<id, { id, text, type, labelType, classes, styles, props }>
db.getEdges()       // [{ start, end, type, stroke, text, labelType, id }]
db.getSubGraphs()   // [{ id, title, nodes[] }]
```

Фактические данные на примере из задачи:

| Что | Значение из `db` |
|---|---|
| Узел A | `type: "square"`, `text: "Пользователь"`, `labelType: "text"` |
| Узел B | `type: "diamond"` (ромб) |
| Узел C `( )` | `type: "round"` |
| Узел D `([ ])` | `type: "stadium"` |
| Ребро `-->` | `type: "arrow_point"`, `stroke: "normal"` |
| Ребро `-.->` | `stroke: "dotted"` |
| Ребро `==>` | `stroke: "thick"` |
| Ребро `---` | `type: "arrow_open"` |
| Ребро `<-->` | `type: "double_arrow_point"` |
| Подпись ребра | `text: "да"` |

Типы фигур, которые отдаёт парсер: `square, round, stadium, subroutine, cylinder, circle, doublecircle, diamond, hexagon, odd, lean_right, lean_left, trapezoid, inv_trapezoid, ...`

`labelType: "string"` = в тексте markdown/HTML (`**bold**`, `` `code` ``, `<br/>`), `labelType: "text"` = простой текст (там `\n` приходит буквально).

**Вывод:** свой парсер Mermaid писать не нужно. Mermaid — источник истины по синтаксису, мы забираем из него нормализованную модель.

`[РИСК]` `db` — внутренний API, не публичный контракт. Может поменяться в мажоре. Митигация: пин версии + снапшот-тесты на `db` (см. §12).

### 2.2 Готовый опенсорс, максимально близкий к задаче `[ПРОВЕРЕНО]`

Нашёл `beautiful-mermaid` (MIT, `lukilabs`, v1.1.3) — делает **ровно наш пайплайн**:

- собственный построчный парсер (не `mermaid`) → внутренняя модель;
- раскладка на **ELK.js**; автор заявляет в README синхронный запуск через обход `workerFactory` (FakeWorker) — **лично не проверял**, только прочитал README и код раскладки;
- **свой SVG-рендерер**, zero-DOM, темы через CSS-переменные;
- бандл ~600 КБ исходников логики: `parser.ts` 645 строк, `layout-engine.ts` 1421, `renderer.ts` 603, `text-metrics.ts` 246.

Замер на примере из задачи: **114 ms**, SVG 5.5 КБ.

Что у него не так для нас:
- шрифт подключается `@import url('https://fonts.googleapis.com/css2?family=Inter...')` — **для экспорта в PNG это ломается** (внешний ресурс внутри SVG-картинки);
- ширина текста считается эвристикой по «классам символов», а не реальными метриками шрифта → для кириллицы Golos/Sans Display будет врать;
- **нет fit-text**: он растит бокс под текст, а нам надо наоборот;
- 13 тем «на любой вкус», нам нужна одна.

**Вывод:** берём как референс архитектуры и как источник идей (особенно §layout-engine и FakeWorker-трюк для ELK), но рендер, метрики и тему пишем свои. Копировать код не нужно, лицензия MIT позволяет.

### 3.3 Рёбра

`[ИСПРАВЛЕНО ПОСЛЕ АУДИТА]` В архиве **две несовместимые системы стрелок** (см. `docs/AUDIT.md`, §2):

| Семейство | Где | Вид |
|---|---|---|
| **A — ортогональная** | `image (5)`, `image (17)`, `image (25)`, `image (8)` | прямые углы, линия **~2 px**, наконечник — **залитый треугольник**, teal или серый |
| **B — безье** | `image (18)`, `image (21)` | **изогнутые** линии, толщина **~1 px**, наконечник — **тонкая «галочка» (stealth)**, тёмно-серый/чёрный |
| `dashed` | `image (11)` (каталог стрелок), `image (25)` | пунктир 4/4, наконечник как у A |

Правила, которые фиксируем:
- **Выбираем систему A (ортогональную)** — она доминирует в архиве и читается как «инфографика Нетологии»; система B — это манера другого автора/инструмента (Figma/Whimsical), в единый стандарт не берём.
- Ортогональность = причина выбрать ELK с `ORTHOGONAL` (§7).
- Подпись ребра — **на белой подложке** (в архиве текст «лежит» на линии и линия под ним не видна) с отступом 4 px.
- Стрелка всегда в конце, размер 8×8, `markerUnits="strokeWidth"` не используем (фиксируем размер, чтобы не «толстела» на жирных линиях).
- `-.->` → `dashed`, `==>` → утолщённая (2.5 px), `---`/`-->` → `neutral`, `-->|label|` → с подписью.

### 3.4 Правила, которых в архиве нет, но они нужны для консистентности

1. Сетка отступов — **8 px** (в архиве отступы 24/32/40, кратно 8).
2. Радиусы: `12` для боксов, `999` для капсул, ромб — без радиуса.
3. Тень — **нет** (в архиве нигде нет теней).
4. Минимальный паддинг внутри узла — `16 px` по горизонтали, `12 px` по вертикали.
5. Бордер — всегда `1 px`. `[ИСПРАВЛЕНО ПОСЛЕ АУДИТА]` Цвет — в семействе A это едва заметный `#D0D7DD` вокруг заливки `#F2F4F6`, в семействе B — **чёрный**. Берём `#D0D7DD` (A).
6. Фокус/«активный» элемент — акцентная заливка **или** акцентный бордер + тинт-подложка, не оба сразу.

## 4. Архитектура решения

Пайплайн (однонаправленный, чистые шаги, каждый тестируется отдельно):

```
textarea (Mermaid)
      │  debounce 300 ms
      ▼
[1] parse      mermaid.mermaidAPI.getDiagramFromText()  ──► db (vertices/edges/subgraphs)
      │                                                     │ ошибка → ErrorPanel
      ▼
[2] normalize  db ──► DiagramIR (наш DSL, версионированный JSON)  ◄── ЗДЕСЬ вся «стандартизация»
      │
      ▼
[3] layout     DiagramIR + measuredTextBoxes ──► Coordinates (elkjs, ORTHOGONAL)
      │
      ▼
[4] render     DiagramIR + Coordinates ──► <svg> (React, без строковой склейки)
      │
      ├──► превью на экране (тот же SVG)
      └──► [5] export: serialize → SVG-file | SVG→canvas→PNG
```

Ключевая мысль: **IR — единственный источник правды для рендера.** Рендерер ничего не знает про Mermaid, а `normalize` ничего не знает про SVG. Благодаря этому:
- можно менять дизайн, не трогая парсинг;
- можно добавить второй вход (свой DSL, AI-генерацию) без переделки;
- IR можно показывать в UI (отладочная панель) — но это опция.

### 4.1 Модули (предлагаемая структура)

```
src/
  app/
    App.tsx                  // 2 колонки: <EditorPane/> <PreviewPane/>
  features/
    editor/
      EditorPane.tsx         // textarea + примеры + счётчики

    preview/

  diagram/

      ir.ts                  // типы DiagramIR + версия
    measure/
      textMetrics.ts         // canvas measureText + кэш
      wrapText.ts            // перенос по словам
      fitText.ts             // подбор размера шрифта  ← требование «не растягивать»
    layout/
      layoutElk.ts           // [3] elkjs, ortho routing, FakeWorker
      layoutTypes.ts
    render/

      edges/Edge.tsx         // путь + маркер + подпись
```

Правило: **цвета/шрифты/радиусы существуют только в `diagram/render/theme.ts`**. Никаких хардкодов в компонентах.

## 5. Спецификация нашего DSL (DiagramIR)

Версионируем с первого дня: `v: 1`.

```ts
type IR = {
  v: 1
  direction: 'TB' | 'BT' | 'LR' | 'RL'   // нормализуем: mermaid TD → TB
  nodes: IRNode[]
  edges: IREdge[]
  groups: IRGroup[]      // subgraph
}

type IRNode = {
  id: string                       // как в mermaid
  role: 'box' | 'accent' | 'pill' | 'round' | 'circle' | 'hexagon' | 'decision' | 'dashed'
  label: TextBlock                 // см. ниже (уже разобранный markdown)
  size: 'auto' | 'fixed'
  parentId?: string                // вложенность в группу
}

type TextBlock = {
  lines: InlineRun[][]             // строки → прогоны с начертанием
}
type InlineRun = { text: string; bold?: boolean; italic?: boolean; code?: boolean }

type IREdge = {
  from: string
  to: string
  label?: TextBlock
  kind: 'solid' | 'dashed' | 'thick'
  arrow: 'end' | 'both' | 'none'
}

type IRGroup = { id: string; label?: TextBlock; nodeIds: string[] }
```

Пример для разметки из задачи:

```json
{
  "v": 1,
  "direction": "TB",
  "nodes": [
    { "id": "A", "role": "pill",     "label": { "lines": [[{ "text": "Пользователь" }]] } },
    { "id": "B", "role": "decision",  "label": { "lines": [[{ "text": "Авторизован?" }]] } },
    { "id": "C", "role": "box",       "label": { "lines": [[{ "text": "Открыть дашборд" }]] } },
    { "id": "D", "role": "box",       "label": { "lines": [[{ "text": "Показать логин" }]] } }
  ],
  "edges": [
    { "from": "A", "to": "B", "kind": "solid", "arrow": "end" },
    { "from": "B", "to": "C", "kind": "solid", "arrow": "end", "label": { "lines": [[{ "text": "да" }]] } },
    { "from": "B", "to": "D", "kind": "solid", "arrow": "end", "label": { "lines": [[{ "text": "нет" }]] } },
    { "from": "D", "to": "B", "kind": "solid", "arrow": "end" }
  ],
  "groups": []
}
```

Почему IR, а не сразу SVG-координаты: IR **не содержит** ни цвета, ни размера шрифта, ни координат — значит его можно снапшотить в тестах и он не будет «переписываться» при каждом изменении дизайна.

`[НУЖНО РЕШЕНИЕ]` Нужен ли пользователю доступ к IR (кнопка «Copy JSON»)? Я бы сделал скрытой фичей для отладки.

## 7. Раскладка

`[РЕШЕНО]` **ELK.js** (`elkjs`) в браузере, алгоритм `layered`, `edgeRouting: ORTHOGONAL`.

Почему не dagre (дефолт mermaid):
- в доминирующем семействе архива (A) многошаговые схемы имеют прямые углы и вертикальные «падающие» стрелки, а не пучки безье (`[ИСПРАВЛЕНО ПОСЛЕ АУДИТА]` — в семействе B они как раз безье, см. §3.3);
- ELK даёт `edgeRouting: ORTHOGONAL` + управляемые `spacing.*` из коробки;
- ELK умеет subgraph'ы как кластеры, dagre — хуже.

Почему не переиспользовать раскладку самого mermaid: она неотделима от их рендера и тянет `dagre-d3-es`/`cytoscape`; нам нужны координаты, а не SVG.

Параметры (стартовые, подгоняются по референсам):

```js
{
  'elk.algorithm': 'layered',
  'elk.direction': 'DOWN' | 'RIGHT',
  'elk.edgeRouting': 'ORTHOGONAL',
  'elk.layered.spacing.nodeNodeBetweenLayers': '56',
  'elk.spacing.nodeNode': '40',
  'elk.layered.nodePlacement.strategy': 'NETWORK_SIMPLEX',
  'elk.layered.edgeLabels.sideSelection': 'ALWAYS_UP',
  'elk.padding': '[top=32,left=32,bottom=32,right=32]'
}
```

Технические детали:
- ELK ставится как `elkjs/lib/elk.bundled.js` и запускается **синхронно** через подмену `workerFactory` (тот самый FakeWorker-трюк из `beautiful-mermaid` `[ПРОВЕРЕНО]`), чтобы не было «мигания» превью. `[РИСК]` трюк неофициальный; если сломается — есть async-путь с дебаунсом.
- Размеры узлов **вычисляются до раскладки** (иначе ELK не знает габаритов): сначала `measure` + `wrap` + `fit` в пределах max-размера, потом ELK получает уже готовые `width/height`.

`[НУЖНО РЕШЕНИЕ]` Поддерживаем ли `subgraph` в v1? ELK-кластеры — это +1 день работы. Предлагаю: в v1 subgraph рисуем **пунктирным контейнером post-hoc по bounding box** участников (без настоящего кластерного лэйаута), в v2 — нормальные кластеры.

## 8. Fit-text (главное требование по UX)

Правило: **размер узла ограничен, шрифт подстраивается.** Обратное (как в mermaid) — запрещено.

### 8.1 Алгоритм

```
для каждого узла:
  maxW = MIN_NODE_W .. MAX_NODE_W        // 120 .. 260 px (зависит от роли)
  maxH = MIN_NODE_H .. MAX_NODE_H        // 56 .. 132 px (для box), для decision меньше текстовая область
  1) wrap при базовом размере (18 px) в ширину (maxW - 2*padding)
  2) если строки влезают в maxH → ширина = фактическая ширина самой длинной строки + padding (но не уже maxW)
  3) иначе бинарный поиск fontSize в [11, 18]:
        wrap(fontSize) → строк ≤ floor(доступная высота / lineHeight(fontSize))
        берём максимальный влезающий
  4) если даже 11 px не влезает → режем строки и ставим троеточие (никогда не переполняем бокс)
```

Детали:
- `lineHeight = 1.3 * fontSize` (из §3.1).
- Для `decision` (ромб) текстовая область — **вписанный прямоугольник** ромба: доступная ширина ≈ `0.6 * width`, высота ≈ `0.5 * height`. Иначе текст вылезает за скосы — это самая частая визуальная ошибка в таких генераторах.
- Для `circle` — вписанный квадрат (`0.7 * d`).
- Метрики — через `canvas.measureText` с реально загруженным Golos Text нужного начертания; результат кэшируется в `Map<`${text}|${size}|${weight}`, number>`.
- `document.fonts.ready` — обязательно дождаться перед первым измерением, иначе померим фолбэк-шрифт и получим «прыжок» после загрузки. `[РИСК]`: пока шрифт грузится, показываем скелетон превью.

### 8.2 Почему canvas, а не библиотека

`fitty`/`textfit`/`fit-text` измеряют **HTML-элементы** через `getBoundingClientRect` и меняют `font-size` до влезания. У нас текст в `<text>`/`<tspan>` внутри SVG, где нет автопереноса — обёртку строк всё равно считать руками. Поэтому библиотека не экономит работу, но добавляет зависимость и вторую правду о метриках.

`[РЕШЕНО]` Свой `fitText.ts` (~80 строк) + `wrapText.ts` (~40 строк), с юнит-тестами на кириллице.

## 9. Экспорт изображения

Две кнопки (обе бесплатны по сложности):

### 9.1 SVG (вектор)

`new XMLSerializer().serializeToString(svgEl)` → Blob → `<a download>`. Плюс: инлайн `<style>` с токенами, шрифт — `@font-face` c **base64 woff2** (подмножество с кириллицей).

### 9.2 PNG

`svgString → Blob(URL) → new Image() → canvas.drawImage → canvas.toBlob('image/png')`.

Масштаб: `2x` по умолчанию (кнопка/дропдаун 1x/2x/3x). Фон: белый по умолчанию (в архиве слайды на белом), чекбокс «прозрачный» — опционально.

`[РИСК]` **Шрифты внутри растеризуемого SVG.** Когда SVG грузится в `Image`, он изолирован: шрифты страницы не видны. Варианты:

| Вариант | Надёжность | Цена |
|---|---|---|
| A. `@font-face` + base64 woff2 внутри SVG | работает в Chrome/FF; Safari — под вопросом | +~30–60 КБ на файл (сабсет) |
| B. Текст → пути (`opentype.js`/`fontkit`) на экспорте | работает везде | +зависимость, текст не выделяется, файл тяжелее |
| C. HTML-оверлей + `html-to-image` | работает | ломает SVG-экспорт, дублирование рендера |

`[НУЖНО РЕШЕНИЕ]` Предлагаю: **A по умолчанию**, и если спайк покажет проблему в Safari — добавить B как автоматический фолбэк для PNG (SVG всегда отдаём с `<text>`).

`[РЕШЕНО]` Отдельный спайк (0.5 дня) до основной реализации: собрать минимальный SVG с base64-Golos → прогнать в Chrome/Safari/Firefox → зафиксировать вывод в документе. Без этого результата остальное писать рискованно.

## 12. Тест-план

1. **Снапшоты IR** (`normalize`): 12 входных mermaid-строк → IR-JSON. Ловит изменения в `db` mermaid при апдейте.
2. **Юнит `fitText`**: длинная кириллица, одно слово без пробелов, цифры, смешанный `bold`+`code`, пустой лейбл. Проверяем: не вылезает за бокс, размер ≥ 11, не режет при `fit`.
3. **Юнит `wrapText`**: переносы, `-`, длинные слова, эмодзи.
4. **Снапшоты SVG** (с `jest-serializer` нормализацией чисел до 0.1) для 5 эталонов.
5. **Playwright**: вставка текста → в превью появился `<svg>` с N узлами; клик «Скачать SVG» → файл скачался и парсится; клик PNG → файл > 0 байт и это PNG-сигнатура.
6. **Негативные**: битый mermaid → плашка ошибки, старый превью не пропадает; 200 узлов → рендер < 2 с.
